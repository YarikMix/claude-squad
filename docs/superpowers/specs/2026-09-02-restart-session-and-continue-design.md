# Перезапуск сессии и продолжение диалога

Форк `YarikMix/claude-squad` от `smtg-ai/claude-squad` v1.0.20 (`ce1ffb4`).

## Контекст

Две проблемы в повседневной работе с десятком параллельных сессий.

**Контекст диалога теряется при подъёме сессии.** Панель запускается командой `tmux new-session -d -s <name> -c <workDir> <program>`, где `<program>` — это `Instance.Program` дословно. Когда tmux-сессия умирает (перезагрузка, `Ctrl+D`, смерть tmux-сервера) и её поднимают заново через `r resume`, стартует чистый `claude` — переписка остаётся лежать в `~/.claude/projects/<slug>/*.jsonl`, но агент о ней не знает. Пользователь набирает `claude --continue` руками в панели.

Проверено, чтобы не строить фикс на догадке: строки `--continue` в апстриме нет ни в одном из 222 коммитов, 21 тега и всех ветвей (`git log --all -S '--continue'` пуст), в дереве `v1.0.19` тоже. То есть это не регрессия 1.0.20, а недостающая возможность.

**Нет способа перезапустить агента, не убив сессию.** Единственный путь сегодня — выйти из программы внутри панели. Но панель и есть процесс агента: его завершение убивает tmux-сессию, cs показывает `error capturing pane content: exit status 1`, и инстанс приходится поднимать заново. Обходной путь `tmux respawn-pane -k` снаружи работает, но требует помнить имя сессии и уходить из TUI.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Как возвращать контекст | Аргументы из конфига, добавляются **только при перезапуске**, не при первом старте |
| Клавиши | `R` в списке инстансов, `Ctrl+X` внутри присоединённой сессии |
| Что делает перезапуск | `tmux respawn-pane -k` — перезапускает процесс в панели, сессию и git не трогает |

Почему аргументы **дополняют** команду, а не заменяют: в `default_program` встречаются свои флаги (например `claude --add-dir ~/projects/cloud/cloud.mail.ru`), и при перезапуске они должны сохраняться.

Почему не при первом старте: в свежем worktree истории нет, и `claude --continue` там завершится с ошибкой, а вместе с ним закроется панель.

Почему `respawn-pane`, а не пересоздание сессии: при нажатии изнутри пересоздание разорвало бы attached-соединение, и пользователь получил бы то самое красное `Session terminated without detaching`. Respawn сохраняет сессию, её имя, PTY и историю прокрутки — пользователь остаётся внутри и видит, как агент поднимается.

## Изменения по файлам

### `config/config.go`

Новое поле:

```go
// RestartArgs are appended to the program when a session is restarted or resumed.
// Applied verbatim; set to "" for programs that have no resume flag.
RestartArgs string `json:"restart_args"`
```

В `DefaultConfig()` — значение `--continue`, согласованное с тем, что `DefaultProgram` возвращает `GetClaudeCommand()`. Пользователи aider или gemini выставляют своё значение или пустую строку.

### `session/tmux/tmux.go`

Поле `restartCommand string` и сеттер `SetRestartCommand(string)`. Пустое значение — фолбэк на `t.program`, тогда перезапуск просто поднимает программу без дополнительных аргументов.

Метод `RespawnPane() error`:

```go
cmd := exec.Command("tmux", "respawn-pane", "-k", "-t", t.sanitizedName, t.restartCommand)
```

Выполняется через существующий `t.cmdExec`, тем же способом, что `set-option` в `Start()`.

В `Attach()`, рядом с проверкой байта 17 (`Ctrl+Q`, строка ~331), добавляется проверка байта 24 (`Ctrl+X`): вызов `RespawnPane()`, ошибка в лог, соединение не рвётся, цикл продолжает форвардить ввод.

### `session/instance.go`

Метод `Restart() error`: проверяет `started`, `Status != Paused` и что tmux-сессия жива, затем зовёт `tmuxSession.RespawnPane()`. Для приостановленного инстанса возвращает понятную ошибку с указанием нажать `r` — respawn мёртвой сессии смысла не имеет.

При создании tmux-сессии (`instance.go:139` и `:214`) вызывается `SetRestartCommand(program + " " + restartArgs)`. Значение приходит из конфига, а не из `state.json`: правка конфига должна действовать на существующие инстансы без миграции состояния.

`Resume()` тоже начинает поднимать программу с аргументами: он передаёт `restartCommand` в `Start()`. Именно там сейчас теряется контекст, когда tmux-сессия не пережила перезагрузку и создаётся новая.

### `keys/keys.go`, `app/app.go`, `ui/menu.go`, `app/help.go`

- `KeyRestart` в перечислении, `"R"` в `GlobalKeyStringsMap`, биндинг с подсказкой `R restart`.
- `case keys.KeyRestart` в `app.go`: `selected.Restart()`, ошибки через существующий `m.handleError`, затем `tea.WindowSize()`.
- В `ui/menu.go` пункт добавляется в `actionGroup` (строка ~134) для инстансов не в паузе, рядом с `KeyResume`.
- В `app/help.go` — упоминание `Ctrl+X` в подсказке, которая уже рассказывает про `Ctrl+Q`.

## Поведение

| Ситуация | Что происходит |
|---|---|
| `n new` | Программа стартует как есть, без `restart_args` |
| `R` в списке | Процесс в панели перезапускается с аргументами; сессия, ветка и worktree не тронуты |
| `Ctrl+X` внутри сессии | То же самое, пользователь остаётся присоединённым |
| `R` на приостановленном | Ошибка с подсказкой нажать `r` |
| `r resume` | Как сейчас, но поднятая программа получает аргументы |
| `restart_args` пуст | Перезапуск работает, программа стартует без дополнений |

## Тестирование

- `session/tmux/tmux_test.go` — `RespawnPane()` формирует ожидаемую команду. В пакете уже есть `MockPtyFactory` и мок `cmd.Executor` из `cmd/cmd_test`, новой обвязки не нужно.
- `config/config_test.go` — дефолт `restart_args` и чтение значения из файла.
- `session/instance_test.go` — `Restart()` на приостановленном инстансе возвращает ошибку; на живом вызывает respawn.
- Перехват байта в `Attach()` юнит-тестом не покрывается: там реальный `os.Stdin`. Проверяется руками — присоединиться к тестовому инстансу, нажать `Ctrl+X`, убедиться, что агент поднялся с продолжением диалога и соединение не разорвалось.

## Доставка

Ветка `feature/restart-and-continue` в форке. Сборка `go build -o ~/.local/bin/cs .`; перед этим проверить, что `~/.local/bin` в `PATH` раньше `/opt/homebrew/bin`, иначе продолжит запускаться brew-версия.

В апстрим предлагать двумя PR и как фичи, а не как исправление: продолжение диалога при перезапуске и хоткей перезапуска. Формулировка «вернуть `--continue`» неверна — апстрим этого никогда не делал.

## Вне объёма

- Профили (`config.Profiles`) — отдельные аргументы перезапуска на профиль. Пока хватает одного глобального значения.
- Определение наличия истории на диске (`~/.claude/projects/<slug>/`) перед добавлением `--continue`. Это привязало бы форк к внутреннему формату Claude Code; вместо этого аргументы не добавляются при первом старте, где истории заведомо нет.
- Перезапуск группы инстансов одной клавишей.
